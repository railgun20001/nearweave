# NearWeave v0.4 传输协议

本协议是一次不兼容重置。只有使用本页标识的 NearWeave 节点可以发现和通信；先前版本的帧魔数、发现标识、局域网前缀、AAD 和 RFCOMM UUID 均不再解析或广播。

固定 RFCOMM 服务 UUID：

```text
6a144fb2-f5c7-507a-8293-a3976e0e1a34
```

## 帧格式

所有整数使用网络字节序。

| 偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | 魔数 `NWV1` |
| 4 | 2 | 协议版本，当前为 `1` |
| 6 | 2 | 保留位 |
| 8 | 4 | JSON 消息头长度 |
| 12 | 8 | 二进制负载长度 |
| 20 | 可变 | UTF-8 JSON 消息头 |
| 后续 | 可变 | 二进制负载 |

限制：

- JSON 消息头最大 256 KiB；
- 单帧二进制负载最大 1 MiB；
- 文件分块固定不超过 48 KiB；
- 文本剪贴板最大 512 KiB。

长度在分配内存前校验。RFCOMM 是无消息边界的字节流，读取方必须先精确读取 20 字节固定头，再读取声明的消息头和负载。

## 消息

- `hello`：设备 ID、显示名称、协议版本和能力列表；支持 RFCOMM 授权局域网链路时附带会话 ID 和 32 字节一次性链路密钥。
- `network_hello`：局域网 TCP 建链后的首个加密消息，包含设备 ID、会话 ID和不可复用的连接 ID。
- `ping` / `pong`：每 30 秒执行一次连接心跳，连续 90 秒未收到 `pong` 时判定失联。
- `disconnect`：一端主动断开时通知对端取消自动重连。
- `clipboard_text`：SHA-256 位于消息头，UTF-8 文本位于负载。
- `file_offer`：传输 ID、文件名、声明大小和来源。
- `file_chunk`：传输 ID与偏移位于消息头，文件字节位于负载。
- `file_complete`：发送端计算的 SHA-256。
- `transfer_ack`：接收端完成校验后的确认或拒绝。
- `transfer_cancel`：中断指定传输任务，携带传输 ID 与原因。
- `transfer_cancel_ack`：返回 `canceled`、`already_completed` 或 `not_found`；已落盘文件不得撤回。
- `share_roots_request` / `share_roots`：只请求和发布授权共享根及其 revision，不递归枚举目录。
- `directory_list_request/response`：按共享根、相对目录与 offset 请求当前层直接子项；每页最多 200 项并返回 `next_offset`。
- `share_file_request`：用户明确点击下载后，请求一个共享根内的相对文件路径。
- `error`：与请求关联或不关联的应用错误。

`hello.capabilities` 使用 `transfer_cancel_v1` 和 `lazy_directory_browse_v1` 协商以上扩展。未协商单任务取消时，取消会退化为断开该设备；未协商按需目录浏览时，文件直传和剪贴板仍可使用，但共享目录入口提示升级。

`ping`、`pong`、`disconnect`、`transfer_cancel` 和 `transfer_cancel_ack` 进入独立高优先级控制队列，不能被文件分块队列阻塞。取消后的 `(设备 ID, transfer ID)` 在接收端保留两分钟；迟到的 offer、chunk 和 complete 被忽略，不关闭设备连接。发起取消后 5 秒未收到确认，任务显示“本机已停止，对方未确认”且不会自动恢复。

## 局域网发现 v1

UDP `37991` 是固定发现端口，支持三类不超过 1 KiB 的 JSON 报文：

所有发现报文的 `magic` 固定为 `nearweave-discovery-v1`，不接受其他值。

- `announcement`：周期广播设备 ID、名称、发现协议版本、Noise 公钥指纹、进程实例 ID 和实际 TCP 端口；
- `query`：手动输入 IP 时发送，包含一次性请求 ID；
- `response`：仅在“NearWeave 连接”开启时响应，与 `announcement` 字段相同并回显请求 ID。

TCP 优先监听 `37992`。端口被占用时绑定系统分配的动态端口，所有广播、查询响应、Noise `hello` 和蓝牙高速链路公告都必须携带实际端口。发现报文只用于定位和界面展示，不建立信任；最终设备身份必须由 Noise 静态公钥验证。

自动发现按每个有效的非回环 IPv4 网卡发送定向广播并每 5 秒刷新目标，包含 Windows 热点虚拟网卡。手动输入 `IP` 时先查询 UDP `37991`；输入明确的 `IP:端口` 时直接建立 TCP。UDP 端口不可用不影响蓝牙或明确端口的 TCP 直连。

## 纯局域网安全连接

纯局域网 TCP 流以 ASCII `NWL1` 开始，随后执行 `Noise_XX_25519_ChaChaPoly_SHA256`：

1. 双方使用每个安装实例长期持有的 X25519 静态密钥完成 Noise XX 握手。
2. 握手后在加密通道中交换设备 ID、名称和本机实际 TCP 端口。
3. 已信任设备必须同时匹配设备 ID 与静态公钥；设备 ID 相同但公钥变化时拒绝连接。
4. 首次连接或任一端缺少信任记录时，双方根据握手摘要和有序设备 ID 生成相同六位验证码。
5. 双方必须分别确认验证码，并在加密通道中交换确认结果；任一端拒绝或 60 秒超时即关闭连接。
6. 确认完成后保存远端设备 ID、公钥指纹和名称。Windows 本机静态私钥使用当前用户范围 DPAPI 加密保存。

Noise 传输消息最大 65535 字节。编码后的 NWV1 帧按不超过 60 KiB 的 Noise 明文块顺序分片，每块带“继续/结束”标记；接收方在解码 NWV1 前必须限制重组后的最大长度。

双方同时发起连接时，以设备 ID 字节序较小的一端发起的连接为首选；另一条连接短暂等待，发现已有连接或配对请求后关闭。TCP 端口变化不能改变设备信任。

纯局域网连接是主控制通道，`hello`、心跳、剪贴板、文件和共享目录消息均经过 Noise 传输。连接断开后优先重新发现局域网端点；同一设备存在可用蓝牙端点时自动回退到 RFCOMM。发送中的当前文件使用相同传输 ID 从偏移零重新发送，接收端必须先清理由该传输创建的 `.nearweave-<UUID>.part`。

## 按需共享目录

- 新版连接建立后只发布共享根，点击根或子目录时才列出该层直接子项。
- 每页最多 200 项，目录优先并按名称排序；客户端对每台设备最多缓存 64 个已打开分页。
- 根 revision 改变或用户刷新时清空对应设备的目录缓存。
- 列目录和下载均拒绝绝对路径、父目录、Windows 路径前缀和符号链接，并重新确认规范化后的目标仍位于当前授权根。
- 点击文件名称不触发传输，只有明确的下载命令才发送 `share_file_request`。

## RFCOMM 授权的局域网高速链路

在没有预先建立 Noise 主连接时，可用已认证的 RFCOMM 会话授权局域网数据链路：

1. 双方在蓝牙 `hello` 中交换本次进程有效的局域网会话 ID 和 256 位随机密钥。
2. 双方通过 UDP `37991` 广播设备 ID、会话 ID和实际 TCP 监听端口；广播不包含密钥。
3. 设备 ID 字节序较小的一端发起 TCP 连接。
4. TCP 首帧使用对端经蓝牙提供的密钥完成 ChaCha20-Poly1305 验证，并校验设备 ID、会话 ID和不可复用连接 ID。
5. 后续每个协议帧使用独立随机 nonce，并把 `nearweave-lan-aead-v1` 作为附加认证数据。

此模式下数据消息优先进入局域网队列，`hello`、`ping`、`pong` 和 `disconnect` 保留在 RFCOMM；局域网队列不可用时回退 RFCOMM。一次蓝牙连接结束时，其 v1 局域网授权和活动 TCP 连接同时失效。

## 版本隔离规则

- 应用帧固定使用 `NWV1`，纯局域网流固定使用 `NWL1`，发现标识固定使用 `nearweave-discovery-v1`。
- 配对码域固定使用 `nearweave-pairing-code-v1`；RFCOMM 授权局域网帧的 AEAD AAD 固定使用 `nearweave-lan-aead-v1`。
- 任一固定标识或协议版本不一致时立即停止业务消息交换，不尝试兼容解析。
- 未识别的固定头、超限长度或不连续的文件偏移属于协议错误。
- 平台适配器可以把协议帧承载在 RFCOMM、BLE 分片或 TCP 上，但不得改变消息语义和文件路径规则。
- `hello.networkOffer` 是可选扩展；没有该字段或没有 `lan_encrypted_tcp` 能力时只使用蓝牙。
- NearWeave v0.4.0 与重置前版本不能相互发现或通信，双方升级到 v0.4.0 后才可重新互联；迁移保留的设备 ID、Noise 身份与信任记录无需重新创建。
